I hated it so much I'd bought a Fire Stick to replace it (and then did the same ADB debloating on the stick).

VIDAA is Hisense's proprietary, locked-down Linux. There's no ADB and no developer mode. And it had two gripes that bothered me to no end:

- **Relentless telemetry** - I'd disabled every tracking toggle in the menus and it still phoned home.
- **Refusing to default to the last input** - no matter what setting I flipped, turning the TV on landed on the ad-infested VIDAA home screen instead of going straight to my Fire TV or PC.

Seeing all the RE writeups, decomp drama, and clones this week made me wonder: given enough free time, tokens (thanks, Global build of Z Code), and a willing[^1] chinese[^2] model like GLM 5.3 Flash, could I get root shell access on this thing? That'd give me a higher sense (Hisense) of the TV, let me finally say *al(vidaa)* (goodbye in Urdu - hence the repo name) to the stock bloat, and open up two real tracks beyond run-of-the-mill ADB:

- a custom home launcher that the TV installs itself
- actual root access for firewalling telemetry and modifying the firmware and boot UI

~300M tokens and a couple hours of running recons on the bridge later, I got the message from our friendly chinese model. Everything lives in [carteakey/alvidaa](https://github.com/carteakey/alvidaa).

## The wall that stops everyone

My spec for the launcher never changed: a clock, my HDMI inputs, and my real apps - nothing else. I wanted something functional, not fancy. A launcher can't be enshittified if it doesn't have a feed.

VIDAA TVs expose a RemoteNow channel (MQTT over TLS) for the official Hisense phone remote app. If you publish an action there, the TV launches an app, switches inputs, or injects remote keys. I'd planned a small web page plus a Python server on my Raspberry Pi speaking RemoteNow, starting from the static credentials in older guides.

On my modern firmware, the TV answered those credentials with an on-screen popup:

> *"Your TV mode is no longer compatible with the version of the app. Please try with the latest version."*

The broker returned an authorization error. I found the first clue buried in an issue thread on an old repo: newer firmware checks the **client certificate's identity at the MQTT layer**, and only accepts the certificate carried by the current official VIDAA Smart TV app. Getting that certificate out of the app package was the first lock.

The certificate alone still wasn't enough. Modern firmware also demands dynamic per-connection credentials derived from the TV's identity and the current time, so a captured login is worthless a minute later. Someone at Hisense clearly had fun designing that handshake. The exact derivation is in the [findings](https://github.com/carteakey/alvidaa) for anyone reproducing it on their own set; the shape is what matters here.

During pairing, the TV pops up a four-digit PIN on screen for you to send back over MQTT. My initial keepalive loop - meant to hold the dialog open while I typed - re-triggered the pairing request every few seconds, and **every re-trigger rotates the PIN**. Five codes died before I realized what was going on: you've got to trigger once, wait, and submit. I also hit a second trap where I could publish fine and didn't hear a word back because this firmware silently rejects wildcard MQTT subscriptions. Once I switched to exact topic strings, the TV started talking back and I captured the long-lived tokens (a two-day access token and a thirty-day refresh token, so you only pair once).

## A TV that installs its own launcher

I built the launcher as a single HTML page drawn on one flat canvas so rendering stays fast on the TV's browser without fighting CSS compositing bugs. The Raspberry Pi pushed configuration and live HDMI signal state over a WebSocket; if the Pi restarted, the clock kept ticking on screen and reconnected on its own.

{% image_cc "./src/static/img/alvidaa/first-light-tv.jpg", "Photo of the TV showing the custom alvidaa launcher at 15:51 with a clock, HDMI inputs, and app tiles", "w-3/4", "First light at 15:51 - clock, inputs, and apps. Also visible: the SETUP tile rendered white-on-white and the remote's on-screen pointer. Two bugs I didn't know I was photographing." %}

The classic hidden installer URL from older posts (`hisense://debug`) doesn't work on this firmware. While reading through a newer VIDAA web-app repo, I found something much better: **the TV browser exposes its internal bridge functions to any web page it opens.**

When my launcher page loads, it detects those globals and renders an install tile on screen. Clicking it makes the TV read its own app registry (`websdk/Appinfo.json`), append the launcher to the list, and write the file back. After one restart, "Home" shows up as a native TV app.

> "woah. i installed and it shows up and works. how can we make this the default app and there is so much to do now… lets branch this whole thing out as a separate repo… and document findings so far like the cert thing and what not. so so much work hahaa lets"

I spun the project out into **alvidaa** and started a lab notebook in [docs/models/50A51HUV/](https://github.com/carteakey/alvidaa/tree/main/docs/models/50A51HUV/09.01O.P0813/findings) where every discovery, trap, and error code got written down the moment it happened. That notebook's the only reason the second half of the weekend worked.

To finish the first version, I added a watcher on the Pi that relaunches my Home app whenever the stock UI appears (leaving about a second of stock screen flash, which is the ceiling when you don't have root), a config allowlist that hides preinstalled junk apps, an icon proxy that caches app logos from the TV's CDN, and a systemd service on the Pi.

## From the browser file bridge to a root boot hook

Later that evening, I sent the prompt that turned a custom launcher project into a root project:

> "look online if firmware hacks exist for vidaa os and see if you can come up with a backdoor to gain root access to my tv"

I couldn't find any published root method for modern VIDAA firmware. [Bananamafia's hisensehax](https://bananamafia.dev/post/hisensehax/) was a great earlier reference for how the browser APIs work, though it stopped short of root. (Everything below was tested on my Hisense 50A51HUV on MediaTek MTK9602; see the [tested-models matrix](https://github.com/carteakey/alvidaa/blob/main/docs/research/TESTED-MODELS.md) for other sets.)

That same browser bridge that'd let my launcher edit the app registry is a general file read/write API exposed to JavaScript. To see what else it could reach, I had the agent build a self-reporting recon page that runs checks in the TV browser and posts the results back to the Pi. I even installed Recon as a native TV app so it sat right in the stock home screen's Recent row, next to *The Mummy* on Tubi:

{% image_cc "./src/static/img/alvidaa/recon-app-tv-home.jpg", "Stock VIDAA home screen showing the Recon app tile in the Recent row", "w-3/4", "The recon probe installed as a native TV app in the Recent row." %}

Four checks opened the root path:

1. **Runtime:** The TV runs on a MediaTek armv7 chip, and its app browser ("odin") is actually Chromium 111 rather than the ancient Chrome build that older guides assumed.
2. **Leaving the sandbox:** When you ask a program for a file it can't open, its error message often includes the full path it tried. One rejected read told us the whole story: the bridge glues a fixed base directory onto the front of every path without sanitizing relative segments, and that base sits on a writable partition. A relative path that steps up out of it walked straight to the real root filesystem, and SELinux is in permissive mode because the boot script explicitly disables enforcement.

{% image_cc "./src/static/img/alvidaa/traversal-write-works.jpg", "TV screen showing recon v2 output: TRAVERSAL WRITE WORKS - root lane open", "w-3/4", "recon v2 output on the TV confirming relative path writes outside the app sandbox." %}

3. **The local bridge service:** The JavaScript functions in the browser are thin wrappers that post JSON to a local helper service. That helper runs as an unprivileged service user, and its own source code sits on a writable partition. While the browser wrappers stamp every request with a rotating secret token, the helper didn't validate that token when a request arrived directly, and it allowed any origin. Read-only system partitions stay protected by dm-verity, while the app, data, and local partitions are all read-write.
4. **The boot hook:** Since the bridge user isn't root, I used our new read access to inspect the TV's boot scripts. One of them, which runs as **root** on every boot, executes a script from a writable partition if that script exists. A shipping firmware image, with a root-executed hook pointing at a directory the browser bridge can write to.

Because that partition is world-writable at boot, the bridge can drop a file straight into it, and **the next cold boot runs it as root**. To make iteration effortless from the couch, I added a one-line endpoint on the Pi that tells the TV to load any URL over our existing MQTT session, so new recon and hook versions could install themselves without touching the physical remote.

We wrote the first root hook, rebooted the TV with the remote, and waited. Nothing happened. When the recon report came back, `/proc/uptime` showed the TV had been running for over a full day. Pressing power on the remote only puts the TV into standby, and standby doesn't re-run the boot scripts.

{% image_cc "./src/static/img/alvidaa/the-plug.jpg", "Hand holding the unplugged TV power cord", "w-1/2", "The highest-leverage thirty seconds of the project." %}

Half a minute later, the TV booted fresh and our unprivileged bridge got `Permission denied` trying to read the hook's log file. Our hook had made its output dumps world-readable and forgotten to change permissions on its own log. Because the log file was owned by root, that permission error proved the script had run as root, and the dumps came back through the bridge with the process map, listening ports, and files that only root can read.

> "bruv. that is insane. … i am getting excited about owning this hardware finally."

## Getting an interactive shell (the five-lock gauntlet)

Running a blind script at boot is clumsy; I wanted an interactive SSH shell from my laptop. The [findings](https://github.com/carteakey/alvidaa) document the setup in detail.

The firmware doesn't ship an SSH server, and its built-in BusyBox was compiled without `nc`, `telnetd`, `wget`, or `httpd`. Thankfully, `/bin/sh` is full GNU bash with `/dev/tcp/<host>/<port>` built right in, giving us a zero-binary TCP client to pull a cross-compiled static **Dropbear** SSH server and static BusyBox from the Pi at boot.

{% image_cc "./src/static/img/alvidaa/busybox-devtcp.png", "Terminal output showing missing busybox network applets alongside working bash /dev/tcp", "w-3/4", "Missing BusyBox network applets vs bash /dev/tcp pulling static binaries over the LAN." %}

The boot log showed Dropbear listening with host keys generated, yet SSH from my laptop timed out - and once it finally connected, it printed `1` and exited immediately. Five separate firmware and Dropbear locks stood in the way:

| Lock | What happened |
| --- | --- |
| **1. Anti-tamper firewall** | Drops all inbound LAN traffic except MQTT and ICMP, and blacklists the debug ports including SSH, Telnet, and DevTools |
| **2. Key path** | Dropbear's `-D` flag *replaces* the `.ssh` directory rather than joining it, so the key was never where it looked |
| **3. Missing `/etc/shells`** | The shell-validity check runs before key auth, and the file it checks against does not exist on this firmware |
| **4. World-writable `/var/local`** | A boot script `chmod 777`s the directory, which makes Dropbear's parent-directory permission walk reject any key stored there |
| **5. The USB gate wearing root's shell** | Root's login shell *is* the physical USB-key gate script: it ran on login, failed its check, printed `1`, and quit |

Each fix is a source patch to our own static Dropbear build, documented in the [findings](https://github.com/carteakey/alvidaa). Every lock was a vendor defense that assumed a different attacker.

SSH landed in hook v10. It refreshes its tools from the Pi at startup, and a ten-line wrapper (`server/tv`) makes interactive shells and one-shot commands effortless from the couch. I haven't pulled the wall plug since.

The TV has 1.2 GB of RAM and 3.87 GB of eMMC storage split across 42 partitions. Verified boot (dm-verity) stays locked and green on the read-only system partitions, while the UI, apps, and configs live on writable partitions:

{% image_cc "./src/static/img/alvidaa/emmc-map.png", "Partition map of the 3.87 GB eMMC showing 42 partitions", "w-3/4", "The 3.87 GB eMMC layout across 42 partitions." %}

| Partition group | Mount / role | Notes |
| --- | --- | --- |
| `p15`, `p20` | `vbmeta` (64 KB) + SquashFS rootfs (36 MB) | Read-only, `dm-verity` enforced (`verifiedbootstate=green`) |
| `p22`–`p24`, `p37` | Vendor libs, `/application` (97 MB), `/usr/local` (245 MB) | Read-only middleware, binaries (`tvmain`, `iptables`), and ODM configs |
| `p38`–`p42` | `/opt` (665 MB), `/var/local` (348 MB), `/APPS` (614 MB), `/OAD` (921 MB) | Read-write ext4 partitions holding apps, the stock UI, our root hook, and OTA staging |

I streamed the verity-protected rootfs and the rest of the partitions straight to the Pi over `/dev/tcp` with `dd` while the TV was running normally. Unpacking them turned up three notable details:

- **Serial-debug CLI key in plaintext:** `/etc/0001-cli-login-aes.pem` sits world-readable inside the SquashFS rootfs image. It wasn't encrypted; it was just unreachable until we had root, and we didn't have to modify a single byte of verified flash to get it.
- **Loewe and CVTE multi-brand ODM files:** Digging through `/usr/local/` revealed configuration files in Loewe's DCL format, service lists for CVTE and Cultraview, a SQLite database named after Hisense's Qingdao campus (`huangdao.db`), and brand theme folders for ~50 TV brands.
- **The stock home UI is a six-line HTML loader:** On `/APPS/channelA/hisenseUI/`, the stock home screen pulls JavaScript bundles into an embedded Cobalt Starboard engine launched by `hisense_stage0.sh`, only re-extracted when an OTA upgrade flag file is present.

## Of course we ran Doom

Our recipe (documented in [DOOM.md](https://github.com/carteakey/alvidaa/blob/main/docs/models/50A51HUV/09.01O.P0813/DOOM.md)):

- **[doomgeneric](https://github.com/ozkl/doomgeneric)** plus a hundred-line C Linux framebuffer backend that opens `/dev/fb0`, memory-maps the buffer, and nearest-neighbor scales each frame to 1080p.
- Cross-compiled with Zig as a **365 KB** static ARM binary alongside Debian's shareware WAD. Since there's no `scp` or SFTP server on the box, I piped the binary and WAD over standard input through SSH and detached it with BusyBox `setsid`.

The next morning it went playable. The remote turned out to be Bluetooth rather than IR: `/dev/input/event3` carries every button press as standard Linux key events. That same day I added a Doom tile to the launcher's app row. Clicking it tells the Pi server to spawn the binary over SSH while the browser page blanks out, and pressing HOME kills Doom and bounces right back to alvidaa. Because the tile lives in `config.json` rather than `Appinfo.json`, OTA channel wipes can't touch it.

## The telemetry shelf (and the OTA tradeoff)

Early on I'd asked the agent to check what the TV sends out when every privacy toggle in the menus is turned off. The full 26-hour capture and firmware walkthrough live in the [companion telemetry post](/blog/alvidaa/alvidaa-firmware-telemetry/); here's the summary:

| Layer | What we found on the TV |
| --- | --- |
| **Local reporting hub** | Almost every daemon (`tvmain`, `systemserver`, `hisenseUI`, `phoenix`, YouTube, `masman`, AirPlay, DLNA) holds an open socket to `hi_logreport_service` on `127.0.0.1:1969`, alongside `mdharvester`, `write_stat`, and `bizm`. |
| **Cloud endpoints** | ~30 `*.vidaahub.com` subdomains in `sdk.js` and `/APPS/domain/domain_list.json` (`ter-jrnl-na` running a Fluentd log collector that received 14 connections with all toggles off, `rsc-ads`, `dvcstatus-dataretrv`, `file-ul`), plus `phoenix` holding a live TLS connection to Tencent Cloud (`43.157.127.133:10443`) and an unauthenticated Mosquitto broker on `0.0.0.0:1883`. |
| **DNS & DoH bypasses** | `/etc/resolv.conf` hardcodes `1.1.1.1` and IPv6 fallbacks, the TV made **447 direct port-53 queries to `8.8.8.8`** in 26 hours bypassing the LAN resolver, and `/APPS/domain/domain_list.json` explicitly configures DNS-over-HTTPS (`dns.google/dns-query`) for `vidaahub.com`. |
| **Localhost bridge risk** | `localhost:9009/service/hiutils` requires no auth and sends `Access-Control-Allow-Origin: *`, while the browser exposes silent app installation to any page. Don't browse the open web on the TV. |

Because the TV bypasses LAN DNS by design, I deployed two layers (`firmware/adguard-blocklist.txt` for per-client AdGuard rules, plus `firmware/tvfw` for the TV's kernel firewall) and built `alvidaa privacy status` to verify them live:

- **Blocking hardcoded DNS & DoH:** Every outbound DNS packet to anything other than my AdGuard Pi is rejected in-kernel, and HTTPS traffic to Google's resolvers is blocked so DoH falls back to standard DNS. (Auditing the live chain a few days later caught two bugs in our own scripts first: `tvfw` initially ran before `/usr/local/bin/iptables` was on the path, and BusyBox `nslookup` returns `0.0.0.0` for AdGuard-blocked hosts.)
- **OTA updates, and the tradeoff they carry:** `ota-tv.vidaahub.com` is blocked at both AdGuard and the TV's kernel firewall so an automatic firmware update can't silently reseal the root hook. This is a choice, not a recommendation: accepting Hisense's fixes means giving up root, and keeping root means declining future security patches. Both are defensible. Make it deliberately, and know which one you picked.
- **Plaintext S3 catch:** Our initial firewall logging rules wrote to the kernel ring buffer, which driver chatter overwrites in minutes. A background loop now drains `dmesg`, and its first catch was the TV calling **spectrum.s3.amazonaws.com** over plaintext HTTP with zero TLS.

## What this opens up

The practical upgrade landed the same afternoon as Doom when the TV joined my tailnet running **Tailscale** as root:

{% image_cc "./src/static/img/alvidaa/tailscale-tv.jpg", "Tailscale admin console with the tailnet IPs and emails blurred out; hisensetv-88b863c83aa5 visible, Tailscale 1.104.4 on Linux 4.19.79, last seen today", "w-3/4", "The TV on the tailnet running Tailscale as root." %}

Once we had root, the launcher didn't need to live on the Raspberry Pi anymore either. A TV launcher that dies when your server reboots is a worse appliance than the one you replaced - loopback doesn't go down. I replaced the Pi's Python server with a single static `armv7` Go binary (`alvidaa-bridge`) started at boot on the TV itself, serving the launcher UI on `127.0.0.1:8770` and talking directly to loopback MQTT while a watcher bounces the stock home screen back to it.

Trying to move the canvas UI directly into the stock `hisenseUI` home engine taught me a harder lesson. On November 3, I thought an append-only script injection into `/APPS/channelA/hisenseUI/index.html` was rendering our 1080p canvas inside the home process. Clearing the Cobalt cache the next day proved otherwise: the stock home runs inside a stripped Cobalt Starboard engine where `HTMLCanvasElement` doesn't exist (`cv.getContext is not a function`), and what I'd actually photographed was the Chromium "odin" browser rendering the launcher via the watcher bounce. On this build, the canvas launcher stays in the browser pointed at `http://127.0.0.1:8770/` (or on a DOM-only route replacement, which a contributor verified on the 75U8QTUK by replacing the launcher route inside `app.js`). I also probed the ten ALSA capture nodes for Snapcast/Librespot and confirmed audio never enters userspace ALSA on this chip (`snd_pcm_readi` returns `EIO` even during active optical and speaker playback).

Meanwhile, other VIDAA owners started sending pull requests. The [compatibility matrix](https://github.com/carteakey/alvidaa/blob/main/docs/research/TESTED-MODELS.md) now covers **16 models across seven chip families** (MediaTek and Novatek), with ten models rooted and our [publication policy](https://github.com/carteakey/alvidaa/blob/main/docs/DISCLOSURE.md) keeping findings public while leaving exploit payloads out of the repo. Newer `09.60` firmware builds block direct browser writes to the app registry behind an API-layer identity check (`client request permission check error, please check appconfig`), while contributors on the newer chips documented an unauthenticated local package-manager socket and binary-free boot persistence via the vendor service list.

## What if it breaks?

The most common question I've gotten is whether this can brick the TV. Because verified boot (dm-verity) stays locked and green, the read-only system partitions are never touched or flashed. Every persistent change lives on writable partitions, giving a five-step rollback ladder:

1. **A boot hook script misbehaves:** `/etc/rc.local` runs `/var/local/otaTest.sh` in the background, so a hung script won't block the TV from booting. Deleting it over SSH or the browser bridge restores stock boot behavior immediately.
2. **A UI edit breaks the home screen:** I keep `index.html.alvidaa-bak` right next to the loader on `/APPS`, and SSH and the browser bridge run independently of the home UI even if the screen is black.
3. **Everything else in user space:** A standard factory reset wipes the read-write partitions back to stock.
4. **Full partition backups:** Before touching anything, I dumped all 42 eMMC partitions over the network and verified their checksums across two machines.
5. **Hardware UART:** If all network paths ever fail, the physical UART pads remain as a last resort, and we already have the challenge-response scripts and AES key from the rootfs dump.

For now, it just said *alvida* to its ads.
