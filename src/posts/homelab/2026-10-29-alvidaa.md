## The wall that stops everyone

The spec came first, and it never changed: **a clock, my HDMI inputs, my real apps — nothing else.** Functional over fancy. A launcher that can't be enshittified because it has no feed to enshittify.

The mechanism existed before the project did: VIDAA TVs expose a **RemoteNow** channel — MQTT over TLS on port 36669, the exact channel the official phone remote app uses. Publish an action, the TV obeys: launch app, switch source, send keys. So the plan was a web page + a small server that speaks RemoteNow. Every guide on the internet does this with static credentials from 2018.

On my 2024+ firmware, the TV answered all of that with a popup:

> *"Your TV mode is no longer compatible with the version of the app. Please try with the latest version."*

MQTT rc 5, Not authorized. Every guide, dead. The key turned out to be buried in issue #6 of a half-abandoned repo: 2024+ firmware checks the **client certificate's identity at the MQTT layer** and only accepts the cert belonging to the current official VIDAA Smart TV Android app (`CN=VidaaAppAndroidV01`). So we pulled the official APK (the mirrors hard-block bots, so the `.apkm` got AirDropped from my phone), dug the keystore out of `res/raw/`, and `openssl pkcs12 -legacy` later, the TV accepted our TLS handshake for the first time.

The cert alone wasn't enough — modern firmware also wants *dynamic* per-connect credentials: an MD5 digest of the TV's MAC, a username XORed with a hardcoded 64-bit constant, a password salted by the digit sum of the unix timestamp. Someone at Hisense had fun with this.

Then the pairing ritual: the TV shows a 4-digit code, you type it in. Except our keepalive — meant to hold the dialog open — re-triggered it every few seconds, and **every re-trigger rotates the PIN**. Five codes died on that hill before the lesson landed: trigger once, wait, submit. (There was also a trap where the TV talked and we were deaf — this firmware silently denies wildcard MQTT subscriptions, so a naive client publishes fine and hears nothing back, ever. Exact topics only.)

After that: paired, tokens captured (2-day access, 30-day refresh — pair once, stay paired), and the bridge was ours. App lists, source switching, key injection, TV state.

Which brings us to the evening of the same day, and the message that turned a launcher project into a root project:

But we weren't starting from zero. We held something nobody had publicly pushed past its intended use: the `HiUtils` file bridge — read/write files, from JS, inside the TV's browser. So we built `recon.html`: a self-reporting probe page, one version per question, each run POSTing what it found back to the Pi. The ladder, in four beats:

1. **Who are you?** MediaTek MTK9602, 4K panel, firmware `V0000.09.01O.P0813` — and the browser is Chromium 111, not the Chrome 77 every writeup (including ours) swore by. The file bridge is sandboxed to `websdk/`. For now.
2. **Can we leave?** A *failed* absolute read leaks its errno; the errno leaks the sandbox base; and `../` walks straight out to the real root. Arbitrary read/write as the bridge's uid, filesystem-wide. SELinux turns out to be *permissive* — the boot script literally calls `setenforce 0`.

3. **What runs here?** The bridge's backend is "phoenix" — a Node.js server running its own source code off a partition we can write. 4. **Is there a door?** In `rc.local` — run as **root** at every boot — this:

## How it actually worked (for normal humans)

The through-line worth noticing: **at no point did anyone break anything.** The TV told us everything, politely, one honest error message at a time.

**The superpowers in the browser.** Your TV's browser gives pages secret powers — JavaScript functions wired straight into the TV, like a hotel room phone connected to the front desk. One of them can read and write files. It's supposed to only reach one small folder — your phone can call room service, not the other rooms.

**The jail that told us where its walls were.** Ask a computer for a file it can't open and it doesn't just say "no" — it leaves a note explaining why, and that note usually includes the full path it tried. We asked for a forbidden file, and the note came back: *"tried to open `/APPS//etc/passwd`."* The jail had just confessed its entire mechanism: it glues `/APPS/` onto the front of every path. So we asked for `../etc/passwd` — in path-speak, "go up one folder." Up, and out. We never picked the lock; we read the instructions printed on it.

**The back door with a welcome mat.** Those browser powers are just translators, forwarding requests to a helper program on a port that only exists *inside* the TV. Every request gets stamped with a rotating secret token, like a wax seal that changes each time. So we captured a stamped request, then replayed it without the stamp. The helper answered anyway — and its "who is allowed to talk to me" settings were wide open, meaning any webpage the TV's browser ever loads could use it. The bouncer checked wax seals at the front door; the back door had no lock and a welcome mat.

**The maintenance door, opened by the manufacturer.** A guest badge isn't root, so we read the boot scripts (thanks, previous step) — the building's morning routine, left on the front desk. In one of them: *if this specific file exists, run it as root.* In a folder we could write to. A leftover update-test hook, armed in shipping firmware. Write the file, reboot, and the TV voluntarily runs our script as admin — every boot, forever. We didn't defeat the security; we used the maintenance entrance, and the only design flaw was assuming no webpage could ever reach that folder.

(The firewall twist — the guard who caught us and turned out to be on our payroll — completes this story two sections down. It's the best one.)

## The whole root chain, technically

For the reader who wants the actual mechanics. The full record with every constant lives in the repo's `FINDINGS.md`; this is the chain, end to end.

**Stage 0 — control.** MQTT/TLS on 36669. The TLS layer accepts any client certificate; the *broker* checks the cert subject at CONNECT and only accepts `CN=VidaaAppAndroidV01` — extractable from the official APK's keystore (`res/raw/client_mobile_android.p12` in current builds, `res/El.p12` in older ones; `openssl pkcs12 -legacy` for the RC2/3DES ciphers). On top of that, per-connect dynamic credentials derived from the TV's MAC and the unix timestamp (MAC-digest client_id, XOR-masked username, digit-sum-salted password — the constants stay in FINDINGS). The 4-digit PIN exchange issues long-lived tokens: 2-day access + 30-day refresh. Two protocol traps: wildcard subscriptions are silently denied (SUBACK "Unspecified error" — exact topics only), and list responses are JSON arrays where a dict-check silently drops them.

**Stage 1 — foothold.** The TV browser exposes ~85 `Hisense_*` shims plus `HiUtils_createRequest` to any page. The file APIs resolve against `websdk/` — enough to write `websdk/Appinfo.json`, i.e. install a web app as a native TV app (self-install via `HiUtils_createRequest("fileWrite", …)`).

**Stage 2 — escape.** `fileRead` on an absolute path fails, and the errno leaks the chroot base: `open("/APPS//etc/passwd") → ENOENT`. `../` escapes to the real root; `../tmp/` write + readback proves arbitrary read/write as uid 314, filesystem-wide.

**Stage 3 — map.** Chromium 111 on armv7, SoC MTK9602. Rootfs is dm-verity squashfs, `verifiedbootstate=green` — read-only partitions untouchable. Read-write: `/APPS`, `/data`, `/var/local`, `/var/tvservice`, `/OAD`. SELinux **permissive** (`rcS.utopia.linux` calls `setenforce 0`). The bridge backend is **phoenix**, a Node.js server (`/opt/pkgs/tv.vidaa.app.phoenix`) running `/APPS/pkgs/tv.vidaa.jsservice.basic/CHA/phoenix.server.js` as `UhisPhoenix` (uid 314, no capabilities, no seccomp). The shims POST `{"api":"fileRead","args":{…}}` to `localhost:9009/service/hiutils` with a rotating `identifier` header — which the raw API turns out not to require, and the endpoint answers `Access-Control-Allow-Origin: *`. Binary reads crash phoenix (supervised restart — `superwatch`), so recon pages POST incrementally.

**Stage 4 — the door.** The boot scripts are readable. `start-hisense.sh` (root, every boot) does `chmod 777 /var/local` — remember that, it matters twice — and `rc.local` (root, every boot) executes `/var/local/otaTest.sh` if present. Write through the bridge, verify by readback, reboot.

**Stage 5 — root.** Boot trap first: standby doesn't re-run `rc.local`; `/proc/uptime` (readable via the bridge) exposes the difference. After a real power cycle: hook v1 runs as root — its own log root-owned (proof by denial), its world-readable dumps readable: `id`, full `ps`, listeners, `/etc/shadow`, the UART gate scripts, `cli_login.sh`'s keystore-wrapped AES + RSA material. Hook v2's applet inventory: busybox has `dd`, `tar`, `reboot`, `mount`, `chroot` — no `nc`, `telnetd`, `wget`, `httpd` — but `/bin/sh` is real bash, and bash has `/dev/tcp/host/port` built in: a raw TCP client with zero binaries. Hook v3 fetches a static musl busybox (with `telnetd`) from the Pi over that primitive at boot.

{% image_cc "./src/static/img/alvidaa/busybox-devtcp.png", "", "w-3/4", "The toolbox inventory, and the way out: no nc, no telnetd, no wget — but real bash, and /dev/tcp built in." %}

**Stage 6 — the shell.** No SSH binary exists anywhere in the firmware and the ro rootfs can't take dynamic linkers, so: dropbear 2025.88 cross-compiled static-armv7 with `zig cc` (gotcha: build libtomcrypt's archives with zig's `ar`, not the macOS host one), `-D /var/local/roothome` relocating `authorized_keys` onto rw storage. Hook v4 ships busybox + dropbear as one payload, fetched at boot over `/dev/tcp` with a retry loop. Then the gauntlet, each rung a separate hook version:

| Lock | What it was | The counter |
| --- | --- | --- |
| Firewall | `FIREWALL_IN_EULAON`: allow MQTT/ICMP/loopback, DROP rest; blacklist 22, 23, 4444, 9222, 12321 | v5: accept rules at the top of INPUT, re-applied in a loop for the first minutes of boot |
| Key path | dropbear's `-D` *replaces* the `.ssh` dir rather than joining it | Key at `/var/local/roothome/authorized_keys`, fixed live over telnet |
| Shell check | dropbear validates the login shell against `/etc/shells`; root's shell is `/usr/local/scripts/rootlogin.sh` | v6: patch the check — the owner decides what root's shell is |
| Perms walk | dropbear's `checkpubkeyperms()` rejects keys under world-writable dirs — and the firmware `chmod 777`s `/var/local` at boot | v8: patch the walk; same rationale, the owner decides where keys live |
| Gate as shell | Session connected — then printed `1` and quit: root's login shell *is* the USB-key gate script | v9's forced command was right and mangled (literal `\"` from shell escaping → "auth OK, silent exit"); v10: drop it — the patched build execs `/bin/sh` directly |

Every hook version installs remotely (`hookinstall.html` pushed over MQTT through `/api/open`), and the previous version is preserved as `otaTest.v1.bak` on the TV — a single rolling backup slot, so the full v1→v10 lineage lives in the session log and FINDINGS.md, not on the box. Three debugging tricks worth keeping: the armv7 dropbear *starts and listens* on the Pi (32-bit compat) — enough to smoke-test flags and files, though the handshake itself resets under emulation, so end-to-end validation still happened on the TV; the fetch retry loop matters because the first three boot-time fetches always hit an unconnected network; and when a session says "auth OK, zero output," suspect your own escaping before the TV's.

## What owning looks like

The honest map, because hype is cheap:

- **What we hold:** boot-time root code execution (persistent, remotely updatable over MQTT, hook lineage backed up on the TV), the file bridge as a local API, captured credentials, remote page loading, remote reboots.
- **The wall that stands:** verified boot, locked and green. The read-only system partitions cannot be modified — and don't need to be. The UI, the ads, the apps: all on the writable partitions. The cage is real; everything valuable was stored outside it.
- **The road:** dump the firmware over the shell into Ghidra. Kill ads in-kernel with the `iptables` binary that ships on the box. Then the real prize — the launcher server moves *onto the TV* (there's a Node runtime right there), the Pi retires, and the last ~1 second of stock UI dies with it.

And the current frontier, live as I write: the TV has no SSH server at all and its busybox lacks `telnetd`, so we cross-compiled a static **dropbear 2025.88** for its armv7 with `zig cc` and shipped it to the hook. The boot log read `TELNETD-OK` / `DROPBEAR-OK`, host key generated — and yet SSH just *timed out*. That word choice was the clue: "refused" means nobody home; "timeout" means someone is catching your packets and dropping them on the floor, silently. The hook had already dumped the firewall rules at boot, and there it was — my favorite find of the night: **Hisense ships its own anti-tamper firewall.** INPUT jumps to a `FIREWALL_IN_EULAON` chain — allow MQTT, ICMP, loopback; **DROP everything else**, with an explicit blacklist of debug ports: 22, 23, 4444, 9222 (Chrome devtools!), 12321. They anticipated exactly this class of attack and locked the debug ports down at the kernel layer. It just defended the wrong direction: the firewall watches the perimeter, and our attack never knocked — it walked in through the web browser, got admin, and then, as the firewall's own administrator, read the blacklist with the firewall's own `iptables` and added our ports to the allow list. The building's security guard caught us, and then it turned out we'd hired him. Hook v5 (installed remotely, lineage preserved) re-applies those rules in a loop for the first minutes of boot, so later boot stages can't quietly reload the firewall around us.

Then the gauntlet cleared, lock by lock (the table above), and the last one was the best: the session finally *connected* — and printed `1`. That's `key_check.sh`'s error code. Root's login shell on this TV is the USB-key gate script itself, so a successful SSH login spawned the gate, which printed its failure and quit. **The gate was wearing root's shell as a costume.** The right fix was a per-key forced command — and my shell escaping mangled it into literal `\"`, producing the eerie "auth OK, zero output." v10 deleted the forced command (the patched build execs `/bin/sh` directly) and the next restart landed the shell.

{% image_cc "./src/static/img/alvidaa/ssh-gate-costume.png", "", "w-3/4", "One layer deeper than expected: connected, and the output is literally `1` — the gate, in root's shell costume." %}

{% update "2026-10-29" %}
**SSH is in.** `ssh -p 2222 -i server/keys/tv_root_ed25519 root@192.168.0.12` lands at a root shell — key-only, from the laptop, every boot. Hook v10 re-downloads its payload at every boot, so nothing races a restart anymore. The jailbreak is done; the plug has not been pulled since the root pull, and it never needs to come out again.

The hostname is the TV's ethernet MAC. Kernel 4.19.79, built August 2025. 1.2 GB of RAM. The `command not found` noise in the first session is just dropbear's non-login PATH — cosmetic, fixed with one export. Then a ten-line wrapper (`server/tv` in the repo, run from the laptop) turned the whole dance into one command from the couch: `server/tv` for an interactive root shell, `server/tv 'cat /proc/mounts'` for one-shots.

Then, the inventory. Full eMMC map, captured in the first sitting:

- **3.87 GB eMMC, 42 partitions**, 1.2 GB RAM
- `p20` — the 36 MB verity-protected squashfs rootfs (the untouchable one, in theory)
- `p22`/`p23`/`p24` — the app and vendor images
- `p38`–`p42` — the big read-write data partitions (where `/APPS`, `/var/local`, and everything we've been living in actually sit)

Your TV's entire root filesystem is now a file on a Raspberry Pi. Unpacked, it started paying rent immediately: `/etc/0001-cli-login-aes.pem` — the decrypt key for Hisense's serial-debug CLI — sitting right there in the extract at mode 444. It was never actually secret; it was just unreadable until you owned the read. The missing `/etc/shells` that cost us a hook version is confirmed by the filesystem itself. Everything Hisense considered root-only is now a file we own. Verified boot stays green, nothing was modified — we didn't change the rootfs, we *read* it. That's the whole lane: own the read, and the write matters less.

**Postcard from the filesystem.** By midnight even the window writing this post had a key — a read-only tour, light touches, three batches. What the place looks like from inside:

- `hostname` answers `hisensetv-88b863c83aa5` — the ethernet MAC. The TV introduced itself.
- `/var/local/rootdumps/` reads like a heist inventory: `shadow` (639 bytes), `cli_login.sh`, `key_check.sh`, `rootlogin.sh` (all 56 bytes of it), the `check_usb_key` binary, both CLI crypto keys.
- `cat /etc/shells` → `No such file or directory`. The lock that cost us a hook version, confirmed by the OS itself, live.
- The telemetry quartet, on disk where the posts will come from: `bizm`, `hi_logreport_service`, `mdharvester`, `write_stat`.
- The firewall's own ledger shows our accept rules for 2222/2323 stacked in duplicate layers — the re-apply loop's fingerprints. Cosmetic; a dedup is hook v11 material.
- `/APPS/channelA/` holds `hisenseUI`, `operation-ui`, `system-ui` — the stock home's UI code, on the writable partition. The ad-strip phase already has its map.

Second tour, deeper. The load-bearing findings:

- **The OTA re-deploy path is dormant right now** — no `/var/local/upgrade/upgradeversionflag` on disk, so direct UI edits would persist today.
- **The OTA switch is already off.** `/OAD/AppUpgradeSwitch.json` reads `"country":"CAN","upgradeFlag":"0","resetFlag":"0"` — server-stamped with an md5. Even the factory-reset switch is 0. Caveats: the file is md5-integrity-checked (naive edits get caught) and the OTA service likely rewrites it from the server — so the iptables freeze remains the real R0, but the manufacturer has this TV's updates switched off at the switch level already.
- **The telemetry launcher is five lines.** `start-hislogreport.sh` in full: *if the binary exists, run it in the background.* `hi_logreport_service` is one `chmod -x` away from silence.
- **The sponsored content is network-fed.** The UI's `static/presetData/` holds one national-info file — the ad tiles aren't shipped in the code, they're fetched. Which means the iptables lane kills the *data*, the code strip kills the *components*, and the two are complements, not alternatives.
- **The DNS blocking has leaks.** The TV's `resolv.conf` points at the Pi (AdGuard) first — then falls back to 1.1.1.1 and three IPv6 resolvers. Any telemetry domain that fails through AdGuard gets a second opinion. Closing the fallbacks (iptables DNS redirect, or router-side IPv6 RA control) just moved up the list.
- **The UI's build card confirms the platform**: `process.env.json` — `BRAND: HIS, AREA: NA, PLAT: 9602`, and a `REPORT: false` flag sitting in the build snapshot, teasing.

**Can the stock UI be edited directly? Yes — we read the gatekeeper first.** The UI is plain web code (`hisenseUI` is 5.0 MB of `index.html`, `process.env.json`, `shared/`, `static/`; operation-ui is 19 MB; system-ui 53 MB), and normal boots never touch it: the re-deploy path in `deploy.sh` only fires when an OTA upgrade flag exists (`/var/local/upgrade/upgradeversionflag`). Two footnotes from reading it as root: an OTA update does `rm -rf` on the entire channel and re-extracts `hisenseUI.tar.gz` from `/OAD` staging — the ad-strip dies with any firmware update, which is the strongest argument yet for freezing OTA before touching a byte; and a boot script chowns the channel back to `UhisApp:UGhisApp` (chmod 750) at every boot, so edits must stay readable by that user. The sequence, when it happens: tar the whole channel to the Pi, canary-edit one string, reboot, verify the TV still boots to UI — then strip.

## Of course we ran Doom

Every owned machine since 1993 owes the same tax, and this TV was overdue. The ultimate root test isn't reading `/etc/shadow` — that only proves you can *read*. Running Doom proves you *own*: a game from 1993, cross-compiled for a chipset its engineers never imagined, drawing straight into the framebuffer of a smart TV, through its own anti-debug firewall, over SSH, from the couch.

The recipe, for the record:

- **[doomgeneric](https://github.com/ozkl/doomgeneric)** — a Doom port with a deliberately tiny porting surface: implement five functions (init, draw, sleep, ticks, get-key) and the whole engine comes along.
- A ~100-line framebuffer backend: open `/dev/fb0`, mmap, nearest-neighbor 320×200 → 1920×1080 every frame.
- Cross-compiled static-armv7 with the same `zig cc` toolchain that built dropbear. The binary is **365 KB** — the entire game, smaller than one wallpaper.
- The shareware `doom1.wad`, md5-verified against the canonical file — freely redistributable, and now freely redistributing on a television.

The deployment was a comedy of a minimal system: the TV has no `scp` (the binary and WAD went over as `cat | ssh 'cat > file'`), no `nohup` (our static busybox's `setsid` covered it), and the framebuffer *refuses `read()`* — vendor fbs are mmap-only — so a 20-line `fbcat` helper became the screenshot tool. Then:

{% image_cc "./src/static/img/alvidaa/doom-living-room.jpg", "", "w-3/4", "The living room. The PS5 standing guard. Doom picking up shotgun shells, full-screen, on a television that was built to sell them." %}

That's the hangar, the HUD, doomguy bleeding in the status bar, and *YOU GOT THE SHOTGUN!* — the shareware attract demo playing itself, because input isn't mapped yet. The remote is the obvious controller: the D-pad already emits `/dev/input` events, and wiring those into `DG_GetKey` is the next rung — after which the last rite presents itself: installing Doom as a first-class TV app through the same `Appinfo.json` self-install the launcher used, so it sits in the app row between YouTube and Spotify. For now, Doom plays itself on a television built to show sponsored tiles, and it does not intend to stop.

## The telemetry shelf

The part I asked about early — *"check what sort of telemetry games they are up to"* — now has names, straight off the TV's own process table: `hi_logreport_service`, `mdharvester`, `write_stat`, `bizm`, plus a `GetAdsID` bridge on the TV's public API. Public research has already flagged VIDAA's viewing-tracking server as having no authentication.

Two findings make the network layer non-optional:

- The file bridge answers **unauthenticated, with `Access-Control-Allow-Origin: *`**, on the TV's localhost — any page the TV browser ever opens has filesystem access as the bridge user.
- The same browser exposes the silent app-install trick to any page. (That's how our launcher installed itself. It works both ways.)

So the wiretap is already in: `iptables` LOG rules on every new outbound connection (v4 and v6), persisted in `/var/local/tvrc` and sourced by the boot hook — the kernel writes a `TVOUT` line for each SYN and a `TVDNS` line for each lookup, straight into the TV's own logs. With telemetry switched off at the settings layer, whatever still hits that log is the honest baseline. The plan from here: a few days of LOG data → resolve the IPs → block everything that isn't firmware updates, in-kernel, from the boot hook — AdGuard as layer one, iptables as layer two, and the fallback resolvers (1.1.1.1 and friends) handled at the router.
